1. **GitOps Flow (slide 7), 45–60 seconds.** This diagram has no notes, and it’s the best place to deliver the abstract’s practical blueprint. Suggested extension for this talk, not a claim about the demo or college: use one Wagtail image, sync it to staging, verify, then promote that same image through a production config PR. Argo follows Git; a registry push by itself is not the deploy instruction.
2. **College Intranet (slide 2), 20–30 seconds.** Keep the Karpenter and pre-warming notes already there. From [Real Python #254, 20:18–22:30](https://youtu.be/LHglAeK8fSI?t=1218), add the lesson that a representative load test plus observability tells you what to change. In the separate telephony workload, the team found a per-node pod limit, not CPU or memory. For Wagtail, use the takeaway “Look at latency and errors as well as throughput”; don’t present Locust, specific observability tools, or unverified acceptance metrics as college facts. If the talk is tight, use the pod-limit anecdote instead of pre-warming rather than telling both.
3. **Why GitOps for Django? (slide 5), 20–30 seconds.** [Deploy Django, 10:48–11:49](https://youtu.be/H7GMjMgue14?t=648) supplies two practical cues: the speaker prefers small roll-forward fixes when practical, and a shared base with Kustomize overlays helps prevent forgotten environment variables. Suggested Wagtail-specific caveat, not sourced to the recording: reverting Git asks Argo to restore the prior declared app version; it isn’t instant and doesn’t reverse a Django migration. A schema change should allow old and new app versions to coexist during rollout.

Optional opening cue: preview the college story and the two questions it raises: how to handle demand, and how to ship the next change safely. Keep Nix and Scaf notes short and leave the original provisioning demo out unless there’s dedicated time.
